# 📐 Skill 验收报告结构规范（skill-acceptance-report-schema） ![版本](https://img.shields.io/badge/版本-v1.5.4-blue)

写验收报告、登记查询台账、核对报告格式与字段。**报告与台账的结构权威**。

## 这是什么（30 秒看懂）

验收跑完会产出一份报告。**报告长什么样由本 skill 定，不由执行者临场决定**——否则同一批验收每次版式都不一样，没法跨轮比较。

本 skill 定义三件事：

| 定义什么 | 内容 |
|---|---|
| **报告结构** | 双层四区：① 覆盖 + 体量账 ② 问题清单 ③ 证据区 ④ 总评 |
| **台账条目** | `status / coverage / scope / size / issues / fixed / note` 七个字段 |
| **严重度语义** | 🔴 阻断 / 🟡 一般 / 🟢 建议，**颜色跟后果走、不跟语气强度走** |

## 为什么这样定

**① 决策在前，证据在后。** 使用者只读 ①② 两段就能拍板要不要修，③ 的证据是给复核用的，不必先读。

**② 结论性证据一律表格化，散文只允许出现在总评。** 因为「每对有结论」的表格天然防「跑了但没结论」的假走查——散文可以写得很像那么回事，表格不行。

**③ `coverage` 字段是防盲区关键。** 裸写「已验收」会让「只跑了结构体检」和「走了路径模拟」不可区分：结构全绿容易被误读为流程验证过。规范原话——**任何修改前列清单等确认，禁止裸「已验收」**。

**④ `size` 必须是 python `len(text)` 字符数。** 🔴 不是 `file_size` / `wc -c`——中文文件字节≈3×字符，混比必出假警报（某多文件 skill v5.9.2 实证同款坑）。

**⑤ 严重度 = 后果类别，不是语气强度。** 「必须具体列出清理候选」是对交付**充分性**的要求，标成阻断级会让一次本该做完的流程被判失败。**阻断符留给「继续做下去会产生错误结果」的事，不留给「做得还不够细」的事。**

## 与姊妹 skill 的关系

四个 skill 是一套，**各司其职、不重复劳动**：

```
                    ┌─────────────────────────┐
                    │  skill-acceptance        │  ← 编排器：定界 → 结构体检 → 场景枚举 → 路径模拟 → 报告与台账
                    │  （唯一入口，从这进）     │
                    └───────────┬─────────────┘
                                │ 按「引用步骤号」消费，不复制方法论
              ┌─────────────────┼─────────────────┐
              ↓                 ↓                 ↓
    ┌──────────────────┐ ┌──────────────┐ ┌──────────────────┐
    │ skill-health-    │ │ path-        │ │ 本 skill          │
    │ audit            │ │ simulation   │ │ （报告版式权威）   │
    │ 结构体检清单      │ │ 场景枚举+    │ │ 双层四区 + 台账    │
    │ + 4 个自动化脚本  │ │ 路径走查     │ │ 七个字段 + 严重度  │
    └──────────────────┘ └──────────────┘ └──────────────────┘
         Phase 1            Phase 2 / 3         Phase 4 产出物
```

| 关系 | 细节 |
|---|---|
| **被 `skill-acceptance` 消费** | 它的 Phase 4 明确「报告结构模板 = 本 skill 的权威定义」 |
| **与 `path-simulation` 的 report-template 共口径不同版式** | 两份服务不同场景、**各自权威、不互相同步**：本文件是**验收报告**（含证据区与体量账），path-simulation 那份是**单目标流程走查**（走查轨迹 + 修复记录为主）。真正共用的只有**严重度带色**这一条 |
| **不消费任何人** | 本 skill 是被引用方，不引用其他 skill 的步骤——所以它能单独读、单独用 |

**关系是双向可查的**：另三个仓的 README 都有「与姊妹 skill 的关系」一节，各自写自己视角（不复制全文，防三份描述漂移）。

## 怎么用

**装上就生效**——`skill-acceptance` 的 Phase 4 会自动指向本 skill 的规范。

想直接用：

```
「写验收报告」/「登记查询台账」/「核对报告格式与字段」
```

**台账 size 归一化**（历史脏值 → `len(text)` 重测，防拿假基线算出假 Δ）：

```bash
python3 scripts/normalize_ledger_sizes.py [ledger.json] [skills_root]
# 默认 ~/workspace/skill-acceptance/ledger.json + ~/.hermes/skills
```

## 适合 / 不适合

| ✅ 适合 | ❌ 不适合 |
|---|---|
| 验收 skill / workflow / 开发方案后写报告 | 想看**怎么验收**（那是 `skill-acceptance`） |
| 登记与查询验收台账 | 单目标流程走查的产出物（用 path-simulation 的模板） |
| 核对别人的报告格式是否合规 | 判断某个 skill 结构健不健康（那是 `skill-health-audit`） |

## 文件结构

```
skill-acceptance-report-schema/
├── SKILL.md                        # 本文件：报告结构 + 台账字段 + 严重度语义
└── scripts/
    └── normalize_ledger_sizes.py   # 台账 size 归一化（按 len(text) 重测 + 探测 n×1024 脏值）
```

## 参考文件

无。本 skill 刻意保持单文件——它被引用的频率高（每次出报告），体量小（5 千字符量级），外迁只会增加一次加载。
